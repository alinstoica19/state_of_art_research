## Problema (cum o formuleaza autorii)
Autorii spun ca DTN-urile actuale sunt proiectate, implementate, testate si validate in mare parte manual, pentru domenii specifice, si generalizeaza slab. Ei afirma ca nu exista un cadru unificat care sa acopere agentic intregul ciclu de viata, de la definirea cazului de utilizare pana la operare. Literatura pe LLM si DTN presupune un DTN static, deja existent, iar evaluarile sunt adesea rulari izolate (II.F). Provocarile enumerate sunt (III.A):
- ciclul de viata static si manual;
- halucinatiile si non-determinismul LLM;
- lipsa de generalizare;
- limitele ferestrei de context.

## Ce propun (metoda, pe scurt)
- **Arhitectura multi-agent:**
  - agenti: Use-Case, Requirement, Applicability Check, Perception, Reflection, DTN Apps Planner, Code-Generator, Validation/Sandbox si Control;
  - toti folosesc aceeasi instanta LLM, cu prompturi diferite;
  - starea este tinuta intr-o Single Source of Truth Memory (SSOT-M) pe filesystem, versionata, cu audit trail (IV, V.D).
- **Doua faze de operare:**
  - Bootstrap Phase cu human-in-the-loop: formularea cazului de utilizare, KPI-uri numerice, verificarea aplicabilitatii DTN, descoperirea retelei;
  - Autonomous Core fara interventie umana: perceptie, reflectie, planificare, generare de cod, validare in sandbox, control.
- **Control in dubla bucla** (paralela cu paradigma ITU/IETF):
  - bucla interna verifica virtual in sandbox: codul trebuie sa compileze, sa treaca testele si sa indeplineasca KPI-urile;
  - bucla externa actioneaza pe reteaua fizica si declanseaza o noua iteratie daca KPI-urile reale nu sunt atinse (virtual-to-real gap) (IV, O4).
- **Principiul "verify-before-deploy":** la esecul actuarii, Control Agent face rollback la starea anterioara si escaladeaza la operator (VII.B).

## Setup experimental (testbed real / emulare / simulare; unelte; scara; date)
- **Infrastructura:**
  - reteaua "fizica" este emulata cu Containernet (noduri ca containere Docker, Open vSwitch) si expusa printr-un serviciu REST/OpenAPI;
  - sandbox-ul este un container pe un host separat, cu acces la socket-ul Docker;
  - orchestratorul este scris in Python cu FastAPI si LangGraph, iar GUI-ul in React (V).
- **Hardware:** trei VM-uri. Management Host si Physical Network Host au fiecare 16 vCPU si 16 GB RAM; Sandbox Host are 8 vCPU si 16 GB RAM; toate ruleaza Ubuntu cu kernel 5.15 (VI).
- **LLM-uri evaluate:**
  - Gemini-3-Pro-Preview;
  - OpenAI: GPT-5 pentru planificare plus GPT-5-Codex pentru cod, si separat GPT-5.2;
  - Claude-Opus-4.5.
  - Fiecare a fost rulat de 30 de ori per caz de utilizare.
  - Istoricul este rezumat peste 150.000 de tokeni; logurile sunt trunchiate la 5000 de caractere per camp.
- **Cazul 1, migrare de serviciu MEC:** 7 switch-uri (s1-s7), 3 clienti, 6 host-uri MEC alternative (A-F) plus host-ul initial; aceeasi IP virtuala, STP activ; migrare la Layer 2. Obiectivul este limitat la RTT (VI.A, Fig. 13).
- **Cazul 2, network slicing:** izolare logica intre doua grupuri de clienti (Fig. 20-21).
- Autorii precizeaza ca implementarea si evaluarea se limiteaza la managementul retelei si optimizarea topologiei (retea IP/L2 emulata). Nu exista functii de core 5G (V, VIII).

## Experimente si metrici
- Success rate (procentul de rulari care gasesc o solutie si actioneaza).
- Numarul de iteratii si de cicluri de corectie a codului.
- Durata fiecarei faze: Planner, Code Generator, Validation, Control.
- Distributia strategiilor alese.
- Rata de succes la prima incercare (single-shot) comparata cu cadrul complet (Tabelul 5).

## Limitari declarate de autori
- Performanta depinde de furnizorii externi de LLM: raspunsuri malformate, latenta de inferenta, fereastra de context limitata, iar datele sensibile trimise la modele publice ridica probleme (VII.A).
- Exista virtual-to-real gap: solutii validate in sandbox pot esua in reteaua fizica, iar sandbox-ul cu resurse insuficiente poate respinge solutii valide (VII.B).
- Agentii nu converg intotdeauna catre algoritmi optimi.
- Calitatea input-ului operatorului este determinanta, iar prompturile au ajuns la sute de linii (VII.C).
- Modelele mai noi nu garanteaza performanta mai buna; exemplul dat este GPT-5.2 (VII.C).
- Ca lucrari viitoare: retele mai mari si multi-domeniu, plus RAN si mobilitate (VIII).

## Steaguri factuale (da / nu / nedeclarat, cu sectiunea din lucrare)
- core 5G implementat (nu model)?: nu - retea IP/L2 emulata cu Containernet; prin "core network management" autorii inteleg managementul retelei si al topologiei (V, VIII).
- UE reale sau emulate?: nu - clientii sunt containere Containernet, nu UE.
- digital twin al retelei?: da - DTN generat de agenti, cu sandbox care reflecta ultimul snapshot al retelei (IV, V.B).
- prezice efectul unei actiuni inainte de a o aplica?: da - validare in sandbox fata de KPI-uri inainte de actuare (O2, IV, V.B).
- executa actiuni automat (bucla inchisa)?: da - Control Agent actioneaza pe reteaua emulata, cu bucla externa de re-verificare si rollback la esec (IV, VII.B).
- multi-site / geo-redundanta / failover de baza de date?: nu.
- evaluare prospectiva (predictie fixata inainte de experiment)?: nedeclarat.
- rezultat masurat la nivel de utilizator (inregistrari, sesiuni)?: partial - RTT client-MEC prin ping (Fig. 14) si conectivitate/izolare intre clienti; nu sunt inregistrari sau sesiuni de UE.
- observa traficul la SCP / proxy?: nu.
